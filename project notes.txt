Yeah — Python can technically do almost everything SQL would do here, so SQL is not necessary for this project.

But for a data-analytics portfolio project, SQL can be a genuinely useful bridge rather than an unnecessary extra step.

Think of it like this:

Without SQL

You could do:

VLR data
   ↓
Python / pandas
   ↓
filter + calculate + aggregate
   ↓
Power Score
   ↓
Streamlit

For example, Python could load all the match data and say:

“Give me G2's Ascent matches from 2026.”

Then pandas does the filtering.

With SQL

You instead have:

VLR data
   ↓
SQLite database
   ↓
SQL → "Give me G2's Ascent matches"
   ↓
Python → calculate Power Score
   ↓
Streamlit

So yes, there is an extra layer.

But the important distinction is that SQL and Python are good at different parts of the job.

Task	SQL	Python
Store lots of structured data	✅	⚠️
Filter data	✅	✅
Group/aggregate data	✅	✅
Join different datasets	✅	✅
Statistical calculations	⚠️	✅
Exponential decay	😐	✅
Build Power Score	😐	✅
Build website	❌	✅
Machine learning later	❌	✅
Why I'd actually use SQL for your project

The biggest reason isn't that SQL makes the VCT project easier.

It's that you're trying to become a data analyst.

SQL is one of those things where having a project that genuinely uses it is much more valuable than saying:

"I know some SQL."

Your VCT project gives you a very natural reason to learn it.

For example, later you could have:

SELECT
    team,
    map,
    COUNT(*) AS maps_played,
    AVG(rounds_for - rounds_against) AS avg_round_margin
FROM map_results
WHERE season = 2026
GROUP BY team, map;

That query basically says:

"For every team and map, tell me how many times they played it and their average round margin."

Then Python takes that result and does the more complicated Power Score calculation.

That's actually a pretty realistic analytics workflow.

And there's another advantage: the data gets bigger

Imagine we eventually have:

10,000 map records

You don't necessarily want Python loading everything and then doing:

df[df["team"] == "G2"]

every time someone clicks something on your website.

Instead, your application can ask the database:

"Give me only the records I need."

SQL is essentially the query layer between your application and your data.

That's why I'd structure yours as:

              VCT DATA
                 ↓
          ┌─────────────┐
          │   SQLite    │  ← stores everything
          └──────┬──────┘
                 │
                SQL
                 ↓
       "Give me G2's Ascent data"
                 ↓
             Python
                 ↓
      Power Score calculation
                 ↓
            Streamlit
                 ↓
              Website
But I don't want to overengineer this

This is important.

We should not use SQL just because "SQL looks good on a resume."

If we're adding 15 database tables, complicated queries, an ORM, etc. just to say we used SQL, then yeah — that's unnecessary.

I'd keep it simple:

SQLite + basic SQL + Python/pandas.

And you'll learn SQL naturally while building the project.

So I'd say SQL is a useful bridge here, not a requirement. It gives us a clean separation:

SQL gets the data → Python analyzes the data → Streamlit presents the data.

And that's a very legitimate data-analyst workflow.
